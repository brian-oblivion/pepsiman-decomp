`POLY_F4` with a 15-bit colour split into 8-bit channels and four corners
given in winding order (the third and fourth corners go to the
primitive's x3/y3 and x2/y2, as `POLY_F4`'s strip order wants), then
`GsSortPoly` into the current ordering table `D_800ACEA8[D_80095750]` at
priority `pri`.

void func_800286B0(u16 col, s16 x0, s16 y0, s16 x1, s16 y1, s16 x2, s16 y2, s16 x3, s16 y3, u16 pri) {

## Levers

- **A pointer local for the primitive.** `poly.x0 = ...` stores at
  `sp`-relative offsets; retail keeps `&poly` in `$s1` and stores through
  it (and a copy in `$a0`).
- **Store order is source order** (round-3 learning, confirmed again):
  writing x3/y3 before x2/y2 moves the stores.
- **The red channel through its own local (`r = col & 0x1F;`).** Without
  it the body is one word short: global-alloc leaves `x1` (from `$a3`)
  without a saved register and spills it with one `sw a3`, where retail
  gives every register parameter a saved register and spills the seventh
  parameter (`lw t0, 0x70(sp)` / `sw t0, 0x28(sp)`, reloaded `lhu` for the
  last store). Found by the permuter (see below); the local changes the
  pseudo numbering/priorities enough to flip which value is spilled.
- Rejected: `s32` for some or all of the coordinates (changes the frame or
  the spill), a K&R definition (identical to the prototype), swapping the
  x2/x3 store order.
