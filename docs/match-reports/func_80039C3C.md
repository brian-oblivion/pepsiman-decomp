## The blocker: a symbol, not the C

The same blocker as func_8003F100. Retail builds the piece table's base
from the symbol splat named, `addiu $v1, %lo(D_800960A8)` then `addiu $s6,
$v1, -0xA0`, and stores through `$s6 + (i + 10) * 16` while the call's
argument walks a second pointer from `D_800960A8`. The source table starts
10 records (0xA0 bytes) before `D_800960A8`, at 0x80096008, which has no
symbol (`config/undefined_syms_auto` has only `D_800960A8`).

With a symbol there, the body below is byte-exact: measured in-tree with a
temporary `__asm__(".globl D_80096008\n.set D_80096008, 0x80096008");` and
`extern GsDOBJ2 D_80096008[];` in place of the `#define` (build `OK: build
matches retail`, 243/243, insertions 0 / deletions 0). That asm line is a
symbol definition in a .c and is not committed. As with func_8003F100, a
symbols-file entry alone would not do: no instruction references
0x80096008, so splat does not write it and the link fails. A linker-side
definition (`D_80096008 = 0x80096008;`) closes this and func_8003F100
(0x800CDC00) together; the operator's call.

Spellings without the symbol, all 9 words short (one saved register and
the second pointer lost, 234 words):

| spelling | result |
| --- | --- |
| `(D_800960A8 - 10)[i + 10]` for the stores | the -160 folds away, one pointer |
| the same with the index in its own `k = i + 10;` | identical |
| a literal `((GsDOBJ2 *)0x80096008)[i + 10]` | folds too, and `ori` for `addiu` |

Everything else in the body was right on the first or second build: the
only other fix was the operand order of the offset sums (`pack[k] +

  and RTL `plus_constant` cancel `(sym - n)[i + n]`, through a separate
  index local and through a literal address. Needs a linker-side symbol.
