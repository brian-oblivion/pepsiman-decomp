# func_8002D0C4 — MATCHED 11/11 (round 1, alpha)

Unit `src/code_1a098.c`. Points three `$gp` globals at a block whose
8-byte header (`BlockHeader`, declared in the unit) gives a word and the byte
offset of a second part, and zeroes a halfword global.

```c
extern u8 *D_800959C0;
extern u8 *D_800959C4;
extern s32 D_800959C8;
extern u16 D_800958E8;

void func_8002D0C4(BlockHeader *hdr) {
    D_800959C0 = (u8 *)hdr + 8;
    D_800959C8 = hdr->unk0;
    /* MATCHING: ... */
    D_800959C4 = (u8 *)hdr + *(s32 *)((u8 *)hdr + 4);
    D_800958E8 = 0;
}
```

## Externs

`D_800959C0/C4/C8` are in `config/gp-symbols.txt` and declared as plain
scalars (`%gp_rel` stores). `D_800958E8` is a `u16` scalar not in the list:
retail stores it with `lui $at; sh $zero,%lo(..)($at)`, and another unit
loads it with `lui $v0; lhu $v0,%lo(..)($v0)` — the same scalar, assembled
both ways by the load/store expansion. Other functions in this unit reach
`D_800959C0`/`C4`/`C8` with `lui <reg>` too; whoever matches them may need a
per-function declaration.

## Levers (order of loads against global stores)

Retail loads `hdr[0]` first, stores `D_800959C0` and `D_800959C8`, and only
then loads the offset word; the `D_800958E8` store sits between that load
and the `D_800959C4` store. Measured:

| C | result |
| --- | --- |
| `hdr->unk0`, `hdr->offset`, store order C0, C8, E8, C4 | 4/11: both loads hoisted to the top |
| the same with C4 before E8 | identical, 4/11 |
| `s32 *hdr`, `hdr[0]`, `hdr[1]` | 3/11: the `hdr[0]` load sinks below the C0 store |
| `hdr->unk0`, `((s32 *)hdr)[1]` | 4/11 |
| `hdr->unk0`, `*(s32 *)((u8 *)hdr + 4)`, order C0, C8, E8, C4 | 10/11 long by a `nop`: offset load below both the C8 and E8 stores |
| **`hdr->unk0`, `*(s32 *)((u8 *)hdr + 4)`, order C0, C8, C4, E8** | **11/11** |

So the first word is a struct member (its load may rise above a fixed scalar
store) and the offset word is read through a byte-pointer cast (its load
may not rise above one). That fits GCC 2.x's `MEM_IN_STRUCT_P` heuristic
(a struct access and a fixed-address scalar are assumed not to alias), but
`((s32 *)hdr)[1]` behaving like the member access is not explained by it;
treat the mechanism as a hypothesis.

### Proposed learning

GCC 2.8.1 keeps a load below an earlier global store only when it cannot
rule out aliasing; a struct member load rises above fixed-address scalar
stores. When retail loads a field late, after global stores, try reading it
through a byte-pointer cast (`*(s32 *)((u8 *)p + K)`); when it loads early,
keep the member access. Then the store order around it decides the rest.
