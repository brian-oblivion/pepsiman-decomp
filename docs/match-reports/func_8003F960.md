record: while the record's delay (`unk2`) is non-zero, count it down and
return 0. Otherwise set the local-screen matrix to (`x`, `y`, `z`) plus the
record's offset (`unkC`, `unkE`, `unk10`), draw sprite `0x11A + frame`

## What matches

Everything except the register for two stack addresses: the `s16`
parameters (`x += p->unkC` gives retail's `addu s0, a2, s0` and the late
`sll`/`sra`), the frame layout (SVECTOR 0x18, CVECTOR 0x20, GsCOORDINATE2
0x28, MATRIX 0x78), the stores, the `(u16)` sprite id (`andi 0xFFFF`), the
`++p->unk0 == 8` tail, and the block order. An early `return 0` inside the
`if` makes 2.8.1 put the countdown block at the end (`bnez` to it); the
`ret` local with `if/else` gives retail's fall-through order.

## The residue

Retail rematerialises `&coord` (`addiu a1, sp, 0x28` before call 1,
`addiu a0, sp, 0x28` before call 2) and `&ls` (`addiu a1, sp, 0x78`,
`addiu a0, sp, 0x78`). The build CSEs each into one callee-saved register
(`addiu s3, sp, 0x28` / `move a1, s3` / `move a0, s3`, then the same
for 0x78). That costs one more saved register (`s5`: save and restore),
moves `p` and `ot` up one register (`s4`/`s5` instead of `s3`/`s4`), grows
the frame 0xB0 to 0xB8 and adds two `move`s: 4 words.

What I measured with a quick scaffold compile (permuter's compile.sh, the
Makefile's flags):

- **A stack address is never CSE'd when the object is at frame offset 0**
  (the first-declared local). Its address is then the bare frame-base
  register, cost 0, so expand_call does not copy it into a pseudo. Every
  other local's address is `(plus base N)`, copied into a pseudo, and CSE
  merges the second call's copy into the first. That explains
  func_8003F8D4 (matched): `coord` is first (remat), `ls` is not (`s3`).
  It does NOT explain this function: retail has `size` at offset 0 and
  still rematerialises both `&coord` and `&ls`.
- The CSE survives every change I tried in the scaffold: no `if`, no tail
  after `GsSetLsMatrix`, no `ot`, no `p` use after the call, constants
  instead of `x/y/z`, `flg` stored first, s32 parameters with `(s16)`
  sums or `s16` locals, a `GsCOORDINATE2 *` local, `coord`/`ls` in an
  inner block (same layout), all aggregates inside the `else`.
- Permuter: one bounded search (`timeout 600`, `-j 4`, 48,573
  iterations, ended by the timeout: rc 124; base 977). Gate 3 checks run: 1 (scaffold compiles and
  scores), 2 (`--debug --stack-diffs`: insertions 6 / deletions 2) and 3
  (funcdiff's real-build line said 7/7 on a shifted function; I read the
  scaffold's disassembly against the in-tree build by eye: same code,
  AGREE). Its best candidates (scores 305 to 605) only reorder
  declarations (moving the frame layout, which is wrong) or move
  `GsGetLs` out of the `else` (changes the semantics): no lead.

func_8003FBE0 (same unit, round 5) has the identical residue, and
func_8003FA88 between them looks like the same template, so one lever
should close all three.

### Proposed learning

- **An object at frame offset 0 (the first-declared local) has its address
  rematerialised at every call (`addiu aN, sp, K` each time); later locals
  have their address CSE'd into a callee-saved register across calls.**
  Declaration order therefore decides `addiu` vs `move aN, sN`
  (func_8003F8D4). Not sufficient: func_8003F960 rematerialises two
  non-first locals by a mechanism still unknown.
