## Why it cannot match in this unit

Retail reads `D_800959C0` and `D_800959C8` as `lui $aN` / `lw $aN,
%lo(sym)($aN)`: a symbolic scalar load that the assembler expanded without
`$gp`. Every retail access of these two symbols, by address:

- `%gp_rel`: 8002CD68 (C8), 8002CDB4 (C0), 8002D050 (C0), and the stores
  in `func_8002D0C4` (matched C). `D_800959C4` is `%gp_rel` in
  `func_8002D16C` / `func_8002D1CC` too.
- `lui` + `lw`/`sw`, never gp: 8002F2D8, 8002FE1C, 8002FEB0, 8002FEDC,
  8002FFA4, 80030020, 80030084, 800300B4, 80030134, 80030160, 800301F0,
  80033804 (`sw` via `$at`), 80033818 (`sw` via `$at`), 8003382C,
  80033AC0, 80033AC8.

The split is by address, not by function shape: everything up to
`func_8002D2C0` uses gp, everything from `func_8002F270` on does not. That
is a translation-unit boundary inside splat's `code_1a098` (the rodata block
`D_80010B7C..D_800112CC` before `func_8002D424` is the likely seam): the
later source file's assembler did not consider the symbols small data.

maspsx decides gp per symbol, globally, from `config/gp-symbols.txt`. Its
only non-gp path for a listed symbol is `sym+offset` with a `.comm` in the
unit, which a plain load never takes. A second declaration of the name
does not compile; a view under another name needs a linker symbol. So the
fix is structural (split the unit at the seam and give the later unit its
own gp view of these names), which is the head's call. Not touched: yaml,
symbols file, maspsx.

Measured: the body built live (`#if 1`) is 18 words, the oracle fails, and
`tools/asm-differ` shows the only differences are the two loads.

### Proposed learning

A global that is `%gp_rel` in one part of a splat unit and `lui`+`lw` (same
register) in another part marks a source-file boundary inside the unit: the
two files saw different small-data declarations. maspsx's global gp list
cannot express both; the unit has to be split.
