# func_80019CD8 — MATCHED (147/147), round 7, runner charlie

Unit `src/code_a0bc.c`. The POLY_FT4 sibling of func_8001B354: draws sprite
`id` of the table `D_800DD0A0` at `pos` as a textured quad (code 0x2C with a
colour, 0x2D raw without one, semi-transparent when the colour's first byte
is not -1), its UVs mirrored by bit 0 (horizontal) and bit 1 (vertical) of
`mode`, linked into `ot->org[otz]`; the primitive buffer `D_800E48D0`
advances by one packet.

## Levers

- **Each vertex store reads its target back (`sh` / `lhu` of the same
  slot / `sh`): the packet pointer is `volatile`**, and the stores are
  chained, `p->x0 = p->x2 = pos->vx;`. GCC 2.8.1's `store_expr` hands a
  chained assignment the value in a register for a plain memory target and
  re-reads the target only when it is volatile. Two statements
  (`p->x2 = v; p->x0 = p->x2;`) and the plain chain both lose the reload to
  CSE (34/147 with every other word right).
- **The order of the UV register copies follows the chain**: retail copies
  `u3` before `u1` and `v3` before `v2`, which is `u1 = u3 = ...;` (chained
  assignment stores right to left).
- The flips are written as plain reassignments in the order retail copies
  the registers (`u0 = u1; u3 = u2; u1 = u3; u2 = u0;`), which is a swap of
  each pair once the earlier values are substituted.

Three builds.

### Proposed learning

- **A chained store that reads its first target back before the second
  store (`sh`, `lhu` of the same slot, `sh`): the target is volatile.**
  `store_expr` keeps the value in a register for a non-volatile memory
  target, so neither a plain chain nor two statements reproduce it. A
  `volatile T *p` packet pointer did. (func_80019CD8)
