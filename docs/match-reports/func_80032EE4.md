## What retail shows, and the hypothesis

- The block addresses are slot-relative: slot `i`'s blocks sit at
  `0x8016D000 + 0x200 + i * 0xB774 + {0x74, 0x38B4, 0x8094, 0xAF74}`,
  sizes 0x3840, 0x47E0, 0x1770 (of a 0x2EE0 region) and 0x800. The whole
  buffer is 0x2285C bytes, func_80033DE8's count. Hence the draft's
  `ToolBuf` / `ToolSlot` view (consistent with `SaveSlot`'s tag at 0x200).
- Retail folds the first ten block addresses to constants but builds the
  last two as `$s0 + 0x1F17C` / `$s0 + 0x2205C` from the base loaded in the
  prologue. Ten is GCC's CSE path length: after ten conditional branches a
  new CSE path no longer knows the base pointer's constant. So the source
  used one pointer local for the buffer, as the draft does, but the draft's
  branch count before those writes evidently differs (the build folds all
  twelve).
- `-1` is rematerialised (`addiu v1, zero, -1`) for the first two compares
  and kept in `$s2` from the third on: also consistent with a CSE path
  boundary after the second branch, which the draft does not reproduce
  (it keeps -1 in a saved register from the first compare).
- The fail block (`close; return -1`) is laid out right after the eleventh
  write's test, and the last write's failure returns its own result
  (`move v0, s0`), not a known -1, through a separate `close`. The draft's
  `if (n == -1) { close(fd); return n; }` is threaded into the shared fail
  block.

Next steps: vary the branch structure (nested `if`s or `&&` chains instead
of `goto fail`, a per-file helper) to move the CSE path boundaries, and
look at how the last write's result reaches `return`.
