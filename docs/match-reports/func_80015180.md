# func_80015180 — MATCHED 106/106 (round 8, echo)

Unit `src/main.c`. Per-frame pad service for the two ports: re-arms the
actuators of a port that has (re)connected (`PadSetAct`, and
`PadSetActAlign` for a DualShock in state 6), blanks a disconnected port's
data to 0xFF, centres analog stick bytes in 0x69..0x97 to 0x80 for an
analog pad (`(id & 0xF0) == 0x70`), and returns port 0's buttons inverted
(port 1's in the top half).

pointer: `sltu` where retail has `slt`, and nothing else in place. Retail's
`slt $v0, $s3, ($s2 + 0x44)` is a signed counter `k < 2` that loop
optimisation eliminated in favour of the `buf + k*0x22` giv, so the source
loops on `k` and indexes `buf[k * 0x22 ...]`; the port number is `k * 16`.
The actuator buffer is a pointer advanced per pass (retail keeps it in its
own register, `$s1`, at the record start); indexed as `act[k * 16]` it was
built from `k` in every use. Last residue: the order of the four
increments at the loop bottom. With `act += 0x10;` as the body's last
statement it landed in the `j` delay slot where retail has the `k*0x22`
increment; moving it into the `for` step after `k++` closed it.

### Proposed learning

- A pointer-shaped loop test with `slt` (signed), not `sltu`: the source
  counted an `s32` and loop optimisation replaced the counter with a giv;
  write the counter and index from it.
- A pointer bumped last among a loop's increments: put it in the `for`
  step after the counter (`k++, act += 0x10`); as the body's last
  statement it comes out before the givs.
