# func_800338D8 — MATCHED 13/13 (round 1, alpha)

Unit `src/code_1a098.c`. Resets records 150..199 of a 200-entry table of
0x48-byte records (`Rec48`, declared in the unit): two signed halfwords at
0x34 and 0x36 to -1 and a byte at 0x41 to 1.

```c
void func_800338D8(Rec48 *recs) {
    u32 i;
    Rec48 *r;

    r = &recs[150];
    for (i = 150; i < 200; i++) {
        r->unk36 = -1;
        r->unk34 = -1;
        r->unk41 = 1;
        r++;
    }

```

## The lever: a separate walking pointer

Retail's loop register points at the BYTE field (`addiu $a0,$a0,0x2A71` =
150 * 0x48 + 0x41) and reaches the halfwords at -0xB and -0xD. Every
indexed form reduces to a register at the record start (`addiu
$a0,$a0,0x2A30`, offsets 0x36/0x34/0x41) and scores 9/13:

- `recs[i].f` in any store order (unk41 first is 7/13);
- `Rec48 *r = &recs[i]` inside the loop;
- an explicit `*(s16 *)((u8 *)recs + i * 0x48 + 0x36)` spelling;
- `(&recs->unk36)[i * 36]` (field base plus index);
- the halfwords as a chained assignment;
- the record array at a nonzero offset in a parent struct;
- an `s32` counter (8/13, `slti`), a `while` loop.

A local pointer set before the loop and stepped with `r++` matches on the
first try. `tools/cctest.py` scored the indexed form 9/13 on 2.6.3, 2.7.2,
2.8.0 and 2.95.2 too (2.91.66 0/13), so it was a source shape, not the
toolchain.

Note the contrast with `func_80033878`: there retail's pointer advance comes
FIRST (`recs += 100;` on the parameter), here it comes after the constants
(`r = &recs[150];` into a fresh local). The neighbour `func_800338A0`
(records 0..199, a third halfword at 0x38) shows the same +0x41 base and
should take the same shape.

### Proposed learning

When retail's loop pointer is biased to a field other than the first one
written (stores at negative offsets from it), the source walked a separate
struct pointer (`r = &tbl[k]; for (...) { r->f = ...; r++; }`); `tbl[i].f`
always reduces to the record start on 2.8.1.
